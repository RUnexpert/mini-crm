# Решения, допущения и ограничения

## Как устроена защита

Принцип: браузер может отправить в Supabase любой запрос. Поэтому каждое правило проверяется в PostgreSQL, а интерфейс только скрывает недоступные кнопки. Код защиты находится в `supabase/migrations/20261106000000_init.sql`.

| Путь изменения | Чем закрыт |
|---|---|
| Чтение таблиц | RLS-политики `*_select` только для роли `authenticated`. У `anon` отозваны все права на таблицы и функции. |
| INSERT/UPDATE объектов и задач | RLS разрешает запись только постановщику (`private.is_manager()`). Права выданы **на уровне колонок**: `objects(name, address)`, `tasks(object_id, title, description, assignee_id)`. Записать `status`, `author_id`, `created_at`, `deleted_at` клиент не может никак: PostgreSQL отвечает `permission denied`. |
| Смена статуса | Только через функцию `change_task_status()`. Прямой `UPDATE status` запрещён правами на колонки, в том числе постановщику. |
| История | Права только `SELECT`. Записи создают триггер при создании задачи и `change_task_status()`. INSERT/UPDATE/DELETE для клиентов запрещены. Дополнительно CHECK-ограничения не пропустят в историю недопустимый переход или возврат без комментария, даже при записи в обход функции. |
| Роль пользователя | Хранится в `profiles.role`. У клиентов есть только SELECT. В `user_metadata` пользователь может писать что угодно, на права это не влияет: тест это проверяет. |
| DELETE | Не выдан никому: удаление мягкое, через `delete_task()` / `delete_object()`. |
| Автор и время | `author_id default auth.uid()`, `created_at default now()`. Колонки недоступны клиенту на запись, поэтому их значения ставит база из JWT пользователя. |
| Исполнитель | Триггер `tasks_validate` пропускает только пользователя с ролью `executor` и не удалённый объект. |

### `change_task_status(task_id, new_status, comment)`

1. Берёт пользователя из JWT (`auth.uid()`) и его роль из `profiles`. Параметры с user_id или ролью от клиента не принимает.
2. `SELECT … FOR UPDATE` блокирует строку задачи. Исполнитель находит только свою задачу: для чужой ответ «не найдена», существование чужой задачи не раскрывается.
3. Сверяет пару «текущий → новый статус» с таблицей из ТЗ и ролью пользователя. Всё остальное запрещено, в том числе постановщику.
4. Для «На доработке» требует комментарий, в котором есть хотя бы один непробельный символ. Обрезаются любые пробельные символы, включая переносы строк и табуляцию.
5. В одной транзакции обновляет статус и пишет одну запись истории.

**Одновременные запросы.** Блокировка `FOR UPDATE` выстраивает запросы в очередь. Второй запрос перечитывает строку, видит уже новый статус и получает отказ. Тест: из 8 параллельных «Взять в работу» проходит ровно один, а при одновременных «Принять» и «Вернуть» от двух постановщиков — тоже ровно один.

### SECURITY DEFINER

Все такие функции работают с `set search_path = ''` и полностью квалифицированными именами. Пользователя они проверяют внутри себя. `execute` отозван у `public` и `anon` и выдан только `authenticated`. Вспомогательные функции лежат в схеме `private`: она не публикуется через API, поэтому их нельзя вызвать как RPC.

### Почему нет рекурсии в RLS

Политики проверяют роль через `private.is_manager()`. Это SECURITY DEFINER функция: она читает `profiles` в обход RLS, поэтому политика `profiles` не вызывает сама себя. Политика объектов смотрит в `tasks`, политика истории тоже смотрит в `tasks`, а политика `tasks` ни на что не ссылается, так что цикла нет. Вызовы обёрнуты в `(select …)`: PostgreSQL вычисляет их один раз на запрос, а не для каждой строки.

## Решения там, где ТЗ допускает варианты

1. **Создание задачи пишется в историю** как переход «— → Новая» (`from_status = null`) с автором задачи. Так в карточке виден полный цикл с самого начала.
2. **Исполнитель обязателен** при создании задачи. Без него задачу «Новая» некому взять в работу.
3. **Постановщик может переназначить исполнителя** в любом статусе, статус при этом сохраняется. История видна **текущему** исполнителю целиком, прежний её больше не видит, как и саму задачу. Имена прежних исполнителей в истории новый исполнитель видит как «—»: профили других исполнителей ему недоступны.
4. **Редактировать реквизиты** (название, описание, объект, исполнитель) постановщик может в любом статусе, включая «Принята». Статус этим путём не меняется.
5. **Комментарий** обязателен только при возврате на доработку. При остальных переходах функция принимает его по желанию, но интерфейс поле не показывает.
6. **Удаление мягкое** (`deleted_at`). Удалённые объекты и задачи скрываются от всех через RLS, история остаётся в базе для аудита. При удалении объекта мягко удаляются и все его задачи, интерфейс предупреждает об этом. Восстановить данные можно только администратору через SQL.
7. **Видимость профилей:** постановщик видит всех, исполнитель видит себя и постановщиков, то есть авторов задач и записей истории. Список коллег-исполнителей исполнителю не раскрывается.
8. **Пустые строки:** название, адрес, имя и комментарий должны содержать непробельный символ. Это проверяется ограничениями CHECK в базе. Длина ограничена: 200 символов для названия, 500 для адреса, 5000 для описания.
9. **Маршрутизация через `HashRouter`:** статика работает на любом хостинге без настройки rewrites.
10. **UI-библиотека — Pico.css:** аккуратные формы, кнопки и тёмная тема без набора компонентов. Отдельные библиотеки для загрузки данных и форм не нужны: хватает хука `useLoad` на 20 строк и нативной валидации форм.
11. **Демо-данные создаются скриптом через API от имени пользователей**, а не SQL-вставками. Поэтому каждый демо-статус получен допустимым переходом. Service role нужен скрипту только для создания учётных записей и ролей.

## Ограничения и что не сделано

- Нет пагинации, поиска и фильтров: при объёме демо-данных они не нужны.
- Нет обновления в реальном времени (Realtime). Данные перечитываются после каждого действия, а после ошибки смены статуса тоже, на случай если статус изменил кто-то другой.
- Нет интерфейса управления пользователями и восстановления удалённого: это делает администратор через Supabase.
- Сессия истекает по стандартным настройкам Supabase Auth: access token живёт 1 час и обновляется автоматически. Если обновить сессию не удалось или API ответил «JWT expired», приложение выходит из аккаунта и показывает «Сессия истекла».
- Тесты `npm run test:db` создают свои данные и затем мягко удаляют их. В базе остаются скрытые записи «ТЕСТ …»: запускать тесты лучше на отдельном проекте или локальном Supabase.
- Подтверждение удаления сделано через нативный `confirm()`. Это просто и доступно, но выглядит не так, как остальной интерфейс.
- Миграция одна, потому что проект новый. Последующие изменения должны идти отдельными миграциями.
