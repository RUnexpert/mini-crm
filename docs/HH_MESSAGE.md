В базе 3 объекта и 6 задач во всех статусах. Все статусы получены через допустимые переходы, так что в истории виден полный цикл, включая возврат на доработку. У каждого исполнителя есть объект, которого он не видит.

**Как устроено.** Все правила проверяет сама база (PostgreSQL + RLS в Supabase), интерфейс только скрывает лишние кнопки:
- исполнитель читает только свои задачи и объекты, где они у него есть;
- записывать в базу может только постановщик, и только разрешённые колонки. Статус, автор, дата и роль клиенту на запись недоступны;
- статус меняет одна функция: она блокирует строку (защита от одновременных запросов), проверяет переход и роль по таблице из ТЗ и в той же транзакции пишет историю;
- история доступна только для чтения, удаление мягкое, история сохраняется.

Всё это проверяют 11 автоматических тестов: они шлют прямые запросы к Supabase от имени разных пользователей, без service role (`npm run test:db`).

**Объяснение для руководителя:** `docs/FOR_MANAGER.md`.
**Решения и допущения:** `docs/DECISIONS.md`. Главное оттуда:
- создание задачи записывается в историю как «— → Новая»;
- исполнитель при создании задачи обязателен; переназначить его можно в любом статусе, и тогда история видна новому исполнителю;
- удаление мягкое: при удалении объекта скрываются и его задачи;
- не сделаны пагинация, поиск и обновление в реальном времени.
